Ivy

Agent evaluation · Handshake AI · Python / FastAPI / Docker

Claim
Freeze scores before writing preference rationales.
Evidence
Require evidence from the running workspace, then check that the explanation agrees with the result.
Disposition
In use

A coding-agent comparison goes wrong when harness states drift, follow-up prompts diverge, or a grader accepts a plausible answer without checking the workspace. Interactive runs still have to stay comparable, and the operator decisions that shaped them have to stay on the record.

I built an operator workstation around staged interaction plans, isolated harness copies, explicit continuation criteria, and independent verification. It records interventions and artifacts, then freezes scores before generating preference rationales. The explanation has to follow the evidence.

The archive

162 completed task folders in my blind-coding archive. The workflow has supported staged comparisons across migrations, debugging, distributed systems, scientific code, and applications.

Each folder preserves the stage plan, continuation criteria, operator interventions, verification, and preference rationale. That audit trail makes it possible to revisit whether both models faced comparable work and whether the final artifacts actually support the grade.

A verification example +

In a dispatch-scheduling comparison, independent checks showed that one solution was not runnable. The other produced a schedule, but still had a conflict between travel and a required meal break.

The useful distinction was between runnability and satisfying the constraints. A generated schedule alone was not enough to establish success.

Learning from the screen

Computer vision & ML tooling · Independent · PyTorch / OpenCV / Python

Claim
Keep learned perception and deterministic search separate.
Evidence
Inspect what the model read before debugging what the solver decided.
Disposition
Public

When a visual agent makes a bad move, one end-to-end prediction does not show whether perception or decision-making failed. I needed intermediate outputs I could inspect and correct.

In Boggle CNN Player, I separated screenshot capture, board detection, tile labeling, and letter and bonus recognition from a deterministic trie-based solver. Misclassified tiles go back into a review and retraining loop. Saved grids and confusion matrices show what the learned components actually read.

The same split shows up in OSRS Learner: annotation tools, synthetic data, YOLO and CRNN workflows, and imitation-learning experiments that combine screenshots, game state, and temporal inputs.

RSHub

Application engineering · Independent · React Native / FastAPI / Java

Claim
Make the integration testable without the live services.
Evidence
The backend includes an in-memory test store for pairing, ingestion, state round trips, and invalid-key checks.
Disposition
In development

Public player APIs cover only part of an Old School RuneScape account. Live slayer state, loot, timers, quests, and collection progress come from the game client, and the companion still has to behave when a service is down.

I worked across the Expo and React Native app, a FastAPI backend, and a Java RuneLite plugin. An app key pairs the clients. The plugin syncs observable state and does not inject gameplay actions. An in-memory backend store covers pairing, ingestion, state round trips, and invalid-key checks without production services.

The contract is testable across three runtimes. Only configured account state is synchronized, and special game modes are excluded. The product is still in development. The public plugin is the piece you can inspect.

Protocol

Make the result inspectable

  1. Define what success means. Turn an open-ended goal into checks another person can apply.
  2. Build the tools to observe it. Keep the inputs, interventions, and outputs available for inspection.
  3. Investigate the failures. Separate model behavior, data problems, and infrastructure faults before drawing a conclusion.
